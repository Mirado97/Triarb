# Промт для новой сессии: Triangular Arbitrage Bot на MEXC

## Задача
Построить бота для треугольного арбитража на бирже MEXC (Python, asyncio).
MEXC выбран потому что комиссии 0% на спот.

## Суть стратегии
Треугольный арбитраж: ищем расхождение цен между тремя парами на одной бирже.
Пример: USDT → BTC → ETH → USDT. Если после трёх обменов получаем больше чем вложили — профит.
Прибыль маленькая (0.02-0.1% за цикл) но много сделок в день.

## Стек
- Python 3.10+, asyncio, aiohttp, orjson
- WebSocket для получения данных (НЕ REST-поллинг — из-за него бывает блокировка IP)
- REST только для выставления ордеров
- Next.js 14 + TypeScript фронтенд (мониторинг в браузере)
- Docker Compose для деплоя
- VPS: Singapore (DigitalOcean), уже настроен

## Архитектура (рекомендованная)
```
MEXC WS (стаканы) → OrderBookFeed → ArbitrageEngine → OpportunityQueue
                                                              ↓
                                               ExecutionEngine → MEXC REST (ордера)
                                                              ↓
                                               MonitoringBus → WebSocket API → Frontend
```

## Критически важные уроки из предыдущего проекта

### 1. WebSocket подписки
- Bybit/MEXC отклоняет весь батч если хоть один символ невалиден
- Всегда батчить подписки по 10 топиков максимум
- Перед подпиской проверять что символ реально существует на этом рынке
- НЕ подписываться на символы одним вызовом на символ — только батчами

### 2. REST клиент
- Не добавлять Content-Type: application/json в сессию для GET-запросов — ломает ответ
- Для публичных эндпоинтов (маркет-дата) создавать отдельную чистую сессию без заголовков
- Для приватных эндпоинтов (ордера) — отдельная сессия с подписью

### 3. Конфиг и окружение
- .env на сервере свой, в git не коммитить
- НИКОГДА не делать replace_all на переменных которые могут встречаться в строках — сломает названия env-переменных
- docker compose restart НЕ перечитывает .env — нужен --force-recreate или build

### 4. Деплой
- После каждого изменения кода обязательно: git pull → docker compose build --no-cache → docker compose up -d
- --force-recreate без build НЕ обновляет код в образе
- Проверять логи сразу после старта: docker compose logs --tail=50 backend

### 5. Публичные API биржи
- Всегда проверять что нужные поля реально есть в ответе API (не доверять документации)
- MEXC/Bybit могут не возвращать ожидаемые поля (например contractType отсутствовал)
- Тестировать REST-вызовы локально перед деплоем

### 6. msgspec / сериализация
- @property методы НЕ сериализуются в JSON — только поля Struct
- Вычисляемые значения для фронта считать на фронте из доступных полей

### 7. asyncio
- asyncio.get_event_loop().time() — это НЕ Unix timestamp, это время с запуска event loop
- Для Unix timestamp использовать time.time()
- WS-клиент start() создаёт задачу но не ждёт подключения — подписки хранить в очереди

### 8. Блокировка IP на MEXC
- Причина: REST-поллинг цен в цикле = тысячи запросов в секунду
- Решение: WebSocket для всех рыночных данных, REST только для ордеров (~3-5 req/sec)
- Не открывать больше соединений чем нужно

### 9. Фронтенд
- tabular-nums CSS для стабильной ширины числовых колонок (без дёргания)
- Тултипы на заголовках колонок открывать вниз (below) — иначе обрезаются навбаром
- Zustand для state management
- Все тултипы и описания на русском языке

### 10. Общее
- Тестировать критические функции локально ДО деплоя
- replace_all использовать с осторожностью — может сломать строковые литералы
- Все ответы пользователю строго на русском языке
- Не предлагать решения без проверки что они реально работают

## Что нужно реализовать

### Минимальный MVP:
1. MEXC WebSocket клиент (переиспользовать паттерн из ws_client.py)
2. Подписка на стаканы нужных пар
3. ArbitrageEngine — расчёт прибыльности треугольника в реальном времени
4. Логирование найденных возможностей (без реального исполнения сначала)
5. Простой фронтенд — список найденных возможностей с прибылью и временем

### После MVP:
6. ExecutionEngine — реальные ордера через MEXC REST
7. Риск-менеджмент — лимиты, стоп-лосс если один из трёх ордеров не прошёл
8. Статистика — сколько возможностей в час, средняя прибыль

## Latency (обязательно)
Отдельный таб LATENCY во фронте с тремя метриками:
- **WS Feed Latency** — задержка от биржи до сервера (время между ts биржи и ts получения)
- **REST RTT** — round-trip time одного REST запроса к MEXC API (пинг раз в 5 сек)
- **Server → Browser** — задержка от сервера до браузера (через WebSocket сообщение с ts)

Цветовая индикация: зелёный <50ms, жёлтый <150ms, красный >150ms.
Latency критична для арбитража — если >100ms на WS, возможность уже закрыта другим ботом.

## VPS геолокация — где ставить
MEXC — сингапурская биржа, серверы скорее всего в **Сингапуре или Гонконге**.

Перед деплоем надо замерить ping из разных локаций до api.mexc.com:
```bash
ping api.mexc.com          # с локальной машины
traceroute api.mexc.com    # посмотреть маршрут
```

Варианты VPS для теста (все на DigitalOcean/Vultr/Hetzner):
- **Singapore** — скорее всего лучший вариант (текущий VPS там)
- **Hong Kong** — альтернатива, может быть ближе к серверам MEXC
- **Tokyo** — вариант если HK/SG не подходят

Как выбрать: поднять тестовый VPS в каждой локации, замерить REST RTT к api.mexc.com,
выбрать тот где меньше. Разница между 5ms и 50ms в арбитраже критична.

Инструмент для замера прямо из кода: REST RTT поллер (как в предыдущем проекте),
только результаты показывать в Latency панели сразу при старте.

### Замеры с Singapore VPS до api.mexc.com (актуальные):
- Ping (ICMP): **~1ms** — сеть отличная
- REST RTT (холодный, с TLS): **~195ms** — первый запрос
- REST RTT (keep-alive, повторный): **~20-50ms** — ожидаемый в работе

Вывод: Singapore VPS оставлять. Для ордеров обязательно использовать
постоянную aiohttp.ClientSession с keep-alive — не создавать новую сессию на каждый запрос.

### Важно про Akamai:
MEXC использует Akamai CDN. Именно Akamai блокировал IP при большом числе REST-запросов
в прошлом проекте, не сам MEXC. WebSocket соединения Akamai не блокирует.
Для REST: использовать одну постоянную сессию, соблюдать rate limits.
